サイバーの技の分類
サイバーとは、対象を意図に沿って操ることである。
しかし「操る」と一口に言っても、その中には多くの異なる技が含まれている。
何かを操るには、まず何を受け取るかを決めなければならない。
これが入力である。
センサーの値、キー入力、音声、画像、通信データ、あるいは人の身振りも入力になる。
入力とは、世界のどの部分をシステムの内側へ取り込むかを決める技である。
次に、取り込んだものをどのように外へ出すかがある。
これが出力である。
画面表示、音、ログ、モーターの動き、照明の点灯、プロジェクターの投影などがこれにあたる。
出力とは、システムの内部で起きた変化を、外界に作用する形へ変える技である。
ただし、入力と出力だけでは不十分である。
操るためには、まず状態を見なければならない。
センサー値を読む、ログを見る、処理の途中経過を可視化する、内部状態をグラフにする。
これらは見るための技である。
見るとは、対象の状態を把握可能な形に変えることであり、操作の前提になる。
一方で、状態をただ見るだけではなく、他者や自分にどう見えるかを整える技もある。
これが見せるための技である。
同じデータでも、点群として表示するのか、地図として表示するのか、アニメーションとして見せるのかで、受け取られ方は大きく変わる。
プロジェクターを「映像を見る装置」ではなく「映像を見せる装置」として捉える関心は、以前から一貫して存在している。
サイバーにおいて、見せ方は単なる装飾ではない。対象の意味を伝え、行動を促し、場の認識を変えるための操作である。
次に、いつ動くかを決める技がある。
これは契、あるいはトリガーの技である。
ボタンが押されたとき、値がしきい値を超えたとき、時刻になったとき、ファイルが更新されたとき、センサーが特定の姿勢を検出したとき、処理が始まる。
トリガーは単なる条件ではない。条件が満たされたときに、動作へ移るためのきっかけである。
GitHub Actions の push イベントで README を自動更新した記録は、このトリガー設計の具体例として扱える。
さらに、何と何を結びつけるかを決める技がある。
これを配線の技と呼ぶ。
配線とは、単にケーブルをつなぐことではない。
データの出どころと行き先を選ぶこと、処理の順番をつなぐこと、画面上の部品と実際の機能を対応させること、複数のシステムの入出力を接続することを含む。
NDIで映像を別PCに送ろうとした試行や、ROS、rViz、WebAPI、GUIを起動手順として結びつけた実装は、この配線の技にあたる。
次に、向きと量を扱う技がある。
これは向量の技である。
一般にはベクトルと呼ばれるが、ここでは「どちらへ、どれだけ」という意味を強調するため、向かう量と書いて向量と呼ぶ。
点群を動かす、流速分布に沿って粒子を流す、カメラ座標を空間座標に変換する、力の向きや速度を扱う。
こうした技は、単なる数値計算ではなく、対象に向きと勢いを与えるための操作である。
また、複数のシステムが互いに作用し合う場面がある。
これが相互作用の技である。
人が身振りをする。センサーがそれを読む。システムが表示を変える。表示を見た人がまた動きを変える。
このように、システムと人、機械と環境、複数の機械同士が互いに影響を与える場合、単独の入力や出力だけでは説明できない。
相互作用とは、関係そのものを設計する技である。
次に、ある仕組みを別の弾みでもう一度呼び出して使う技がある。
これは再帰・呼出の技である。
ループ、コールバック、イベントハンドラ、関数呼び出し、再帰処理などがここに含まれる。
重要なのは、同じ処理が一度きりで終わるのではなく、条件や結果に応じて再び呼び出される点である。
種から枝葉が伸び、枝葉からまた種が生まれ、そこからさらに枝葉が伸びるように、単純な規則が繰り返し使われることで複雑な構造が生まれる。
そして、多数の対象をまとめて扱う技がある。
これが並列の技である。
一つ一つの点を個別に動かすのではなく、点群全体を一つの場として扱う。
画像の各画素をまとめて処理する。
二次元フィルターをかける。
複数の処理を同時に進める。
並列とは、数の多さを力に変える技である。
TouchDesignerで点群や画像処理を扱ってきた記録は、この並列性の実践として再配置できる。
最後に、変化の調子を扱う技がある。
これは勢いの技である。
ゲイン、ディレイ、減衰、ばね、硬さ、粘り、応答速度、なめらかさなどがここに入る。
値が変わるだけでは、まだ動きにはならない。
どれくらい速く変わるのか。
遅れて反応するのか。
跳ね返るのか。
粘るのか。
すぐ止まるのか。
この調整によって、同じ処理でも印象は大きく変わる。
点群にノイズを与え、それをばね振動のように増加・減衰させた試行は、乱れを意味のある振る舞いに変える例として使える。
以上の十一の技は、ばらばらの分類ではない。
実際のサイバー的な操作では、これらは重なり合って現れる。
たとえば、GUIのボタンを押してレーダーの表示を立ち上げる場合を考える。
ボタンは入力であり、クリックはトリガーである。
ボタンと処理を結びつけるのは配線である。
rVizやブラウザに表示されるものは出力であり、同時に見るための技でもある。
営業担当者に分かりやすく見せるなら、見せ方の技も必要になる。
裏側では複数のプロセスが立ち上がり、通信し、状態を更新する。そこには相互作用、再帰、並列、勢いの調整が含まれる。
つまり、サイバーの技とは、単一の機能名ではない。
対象を望む状態へ近づけるために、入力を据え、出力を整え、状態を見て、見せ方を調整し、きっかけを定め、要素を結び、向きと量を扱い、相互作用を設計し、処理を再び呼び出し、多数を並べて扱い、変化の勢いを調律する。
この一連の技を組み合わせることで、はじめて「操る」という行為が成立する。

この節は、かなり使えます。
次にやるなら、各分類を1つずつ「定義 → 代表例 → TouchDesigner/GUI/プロジェクション/AIエージェントでの例 → 陰陽術っぽく言うなら何か」の順で展開すると、章として強くなります。

なぜサイバーの技を分類するのか
サイバーの技を分類する理由は、プログラムや技術を「どう作るか」ではなく、何をしたいのかから捉えるためである。
多くの場合、プログラムや技術は「どう実装するか」で分類される。
使用言語、ライブラリ、アルゴリズム、フレームワーク、通信方式、データ形式などである。
もちろん、それらは実装のためには重要である。
しかし、これから何かを作ろうとする人が、最初からその実装方法を知っているとは限らない。
むしろ、実装方法が分からないからこそ調べるのである。
そのとき、最初に手元にあるのは「どうやって作るか」ではない。
最初にあるのは、

何かを見たい
何かを見せたい
ある条件で動かしたい
複数のものを結びつけたい
多数のものをまとめて動かしたい
動きの勢いを調整したい

といった、どうしたいかである。
したがって、サイバーの技を整理するなら、分類の軸は「How」ではなく、「Want」であるべきだ。
つまり、「どうやって実装するか」ではなく、何をどうしたいのかを起点にする。
ここで、「何を」の部分はできるだけ固定しない方がよい。
なぜなら、技術は対象をまたいで使い回されるからである。
Aを見えるようにするために作った仕組みは、Bを見えるようにするためにも使えるかもしれない。
Aを動かすためのトリガー設計は、Bを動かすためにも応用できるかもしれない。
点群をまとめて扱うための考え方は、画像、音、ログ、センサー群、AIエージェント群を扱うときにも応用できるかもしれない。
つまり、技は「対象」ではなく「願い」によって再利用される。
だからこの分類では、
「何を、どうやって、どうしたいか」のうち、
主にどうしたいかに着目する。
入力したい。
出力したい。
見たい。
見せたい。
きっかけで動かしたい。
結びつけたい。
向きや量を扱いたい。
相互作用させたい。
もう一度呼び出したい。
まとめて扱いたい。
勢いを調整したい。
このような「どうしたいか」を軸にして技を分けることで、実装方法をまだ知らない人でも、自分の願いに近い技を探しやすくなる。

この分類は絶対ではない
ただし、この分類は絶対的なものではない。
これは数学の公理体系のように、一度決めたら動かせない分類ではない。
むしろ、武道における技の分類に近い。
武道では、突き、蹴り、投げ、受け、崩し、間合い、足さばきなど、さまざまな分類がある。
しかし、流派によって分け方は異なる。
空手の突きとボクシングのパンチは、どちらも「手で相手を打つ」技である。
だが、姿勢、力の出し方、間合い、目的、身体の使い方は異なる。
同じように、サイバーの技も、流派によって分け方が変わってよい。
ある人は「制御」を大きな分類にするかもしれない。
別の人は「観測」と「表示」を一つにまとめるかもしれない。
また別の人は「通信」「記憶」「予測」「生成」を独立した技として扱うかもしれない。
それでよい。
重要なのは、この分類が唯一正しいということではない。
重要なのは、区別して考えることで議論しやすくなることである。
何を入力として扱っているのか。
何を出力として扱っているのか。
これは状態を見ている話なのか、見せ方を整えている話なのか。
トリガーの話なのか、配線の話なのか。
向きと量の話なのか、相互作用の話なのか。
並列処理の話なのか、勢いの調整の話なのか。
このように分けておくと、いま自分がどの問題について考えているのかが分かりやすくなる。

分類は、使い回すためにある
サイバーの技を分類するもう一つの理由は、技を使い回しやすくするためである。
あるプログラムは、特定の対象のために作られる。
たとえば、点群を見せるためのプログラム。
レーダーのデータを表示するためのGUI。
音声に反応して映像を動かす仕組み。
ジェスチャーでマイクをON/OFFする仕組み。
しかし、それらを対象ごとに閉じたものとして扱ってしまうと、別の場面で使い回しにくくなる。
一方で、それを「何をしたい技なのか」で捉え直すと、再利用しやすくなる。
点群を見せる技は、ログを見せる技にもなる。
ジェスチャーをトリガーにする技は、音声や時刻をトリガーにする技にもなる。
プロジェクションの位置合わせは、AR表示やロボットの座標変換にもつながる。
ノイズを与えて動きを作る技は、点群だけでなく、音、照明、UIアニメーションにも応用できる。
つまり、技を対象から切り離し、願いによって分類することで、別の対象へ移植できるようになる。
これは、ソフトウェアの協業にも役立つ。
ある人が「入力の問題」を扱っているのか、「見せ方の問題」を扱っているのか、「配線の問題」を扱っているのかが分かれば、議論が整理される。
複数のプログラムやモジュールを組み合わせるときにも、どの技がどの役割を担っているのかが見えやすくなる。

分けることで、違いを語れる
分類の効用は、同じように見える技の違いを語れるようになることにもある。
武道でいえば、空手の突きとボクシングのパンチは、どちらも手で打つ技である。
しかし、同じではない。
足の置き方、腰の使い方、力の伝え方、距離、連打の考え方、防御との関係が違う。
それでも「手で打つ技」として並べるからこそ、違いを議論できる。
もし突き、蹴り、投げ、受けをまったく分けずに語れば、何について話しているのか分からなくなる。
サイバーの技も同じである。
同じ「見る」でも、デバッグのために内部状態を見るのと、観客に見せるために映像を整えるのでは違う。
同じ「動かす」でも、トリガーで一度だけ動かすのと、ゲインやディレイを調整して滑らかに動かすのでは違う。
同じ「結びつける」でも、ケーブルをつなぐこと、APIをつなぐこと、GUIのボタンと処理をつなぐこと、意味と表示をつなぐことは、それぞれ異なる。
分類することで、これらの違いを混ぜずに議論できる。

要するに
この十一分類は、サイバー技術を固定的に閉じ込めるためのものではない。
むしろ、技を探し、比べ、使い回し、議論するための仮の棚である。
プログラムを「どう作るか」から探すのではなく、
「何をどうしたいか」から探す。
対象ではなく、願いで分ける。
実装方法ではなく、作用で分ける。
流派ごとの違いは認める。
だが、区別して考えることで、議論と協業をしやすくする。
