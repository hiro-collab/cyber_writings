# 読み換え語メモ

## 0. このファイルの位置づけ

このファイルは、本文へ反映する前に、本書で使う読み換え語の扱いを整理するための作業メモである。

固定訳語表ではない。標準訳語を提案する一覧でもない。

英語由来・カタカナ由来の専門語が本文中でどのような役割を持っているかを見て、日本語話者が意味を読める語へ一時的に読み換えるための候補を整理する。

このメモの内容は、本文の意図や著者の明示指示より上位には置かない。本文へ反映するときは、章ごとの流れ、読者の理解、既存訳との関係を確認する。

## 1. 基本方針

本書では、英語由来・カタカナ由来の専門用語を、日本語話者が体感的に意味を読める日本語・漢語へ読み換える。

目的は、専門語を消すことではない。

英語の語が担っている働きや場面を、日本語でも読める形にすることである。

そのため、読み換え語は一語一訳ではない。文脈に応じて使い分ける。

既存訳も、原則として否定しない。既存訳が有効な場面と、既存訳だけでは見えにくくなる働きを分けて説明する。

## 2. 重要な読み換え候補

本文で使う語は、次の四種類に分けて扱う。

- 標準訳語: 一般に使われている訳語。例: 命令、関数、要求、要求仕様、制御、操作。
- 補助説明語: 標準訳だけでは伝わりにくい感覚を補う語。例: 願い、お願い、望み、働き。
- 本書の作業語: 本文内の議論を進めるために仮に置く語。例: 代理演算役、符文、契、向量。
- 比喩語: 構造を見やすくするための比喩。例: 陰陽師、魔法、魔人（ジン）、杖、ランプ。

## 3. 各語の注意

### computer / 代理演算役

`代理演算役` は、本書の作業語である。AI エージェントだけを指す比喩ではない。

`computer` を、単なる機械名ではなく、人の代わりに計算・演算を担う役として読むための候補である。

「電子計算機」という訳は、現代の装置名としては有効である。一方で、`human computer` のような語を考えると、`computer` を最初から電子機械として固定するだけでは、計算を担う役という感覚が見えにくくなる。

本文へ反映するときは、既存訳を誤訳と断定せず、実装形態を表す語としての有効性と、役割性を見えにくくする限界を分けて説明する。

### trigger / 契

`契` は、本書の作業語である。trigger の固定訳ではない。

本書では、何かが動き出すための取り決め、作動条件、きっかけ、条件と動作の結びつきをまとめて説明する語として検討する。

関連する一般語には、trigger、event、condition、hook、callback などがある。

本文へ反映するときは、`契` を陰陽師らしい語として採用するのではなく、作動条件を漢字で読めるようにする試みとして説明する。

### vector / 向量

`向量` は、本書の作業語である。日本語の標準訳ではない。

ただし、「向かう量」と読めるため、向きと量を持つ概念であることを漢字から推測しやすい。

本文では、ベクトル、ベクトル場、流れ、力の向き、点群の移動方向などを扱う技の説明語として検討する。

初出時には、一般的な日本語技術文書では `ベクトル` と呼ぶことを明示する。

### code / 符・符号・符文

`code` は文脈によって意味が広い。

通信、暗号、識別子、規則体系、ソースコード、文字コードなどを一語で扱うため、常に同じ語へ置き換えない。

候補:

- `符`: しるし、記号、作用を起こす記号として扱う場合。
- `符号`: 情報を一定の規則で表す体系として扱う場合。
- `符文`: 人が書き、機械が読み、処理や作用を起こすまとまりとして扱う場合。

`符文` は造語に近いため、本文で使う場合は、標準訳ではなく本書内の作業語であることを明示する。

### function / 働き・機能・ふるまい

`function` は、数学では `関数` と訳すのが自然な場面がある。

一方、プログラミング入門や読者の体感に寄せる場面では、`働き`、`機能`、`ふるまい` と説明した方が意味が見えやすい場合がある。

本文へ反映するときは、数学的な `関数` を否定せず、場面によって使い分ける。

### command / 命令・指示・願い・依頼・指令

`command` は、対象に何かをさせる表現である。

`願い` や `お願い` は、`command` / `instruction` を生活感覚で説明するための補助説明語である。`命令` や `指示` の標準訳を廃止する提案ではない。

本来、`command` は「命令」でよい。一部の `instruction` も、文脈によっては「命じる」「命令する」と読んでよい。ただし、最初に「命令」とだけ紹介すると、読者にはなぜ命令できるのかが見えにくい。そのため導入時には、「こうしてほしい」というお願いとして掴ませる。

ただし、すべてを `願い` や `お願い` と読むと、命令、権限、実行制約、拒否不能性の感覚が薄れる場合がある。

逆に、すべてを `命令` と読むと、生活語として硬くなり、読者に距離が出る場合もある。

したがって本文では、まず「お願い」で行為の向きを掴ませ、サイバー領域の統治、権限、形式、実行条件を説明したうえで、「命令」「命じる」へ戻す流れを基本にする。

本文では、対象との関係に応じて訳し分ける。

例:

- 実行系に渡す厳格な命令: 命令 / 指令
- UI や対話で渡す要求: 指示 / 依頼
- 「こうなってほしい状態」を伝える場面: 願い / 望み / 目的状態

### requirement / 要求・要求仕様

`requirement` は、標準訳語としては `要求` または文脈によって `要件` でよい。

`requirement specification` は、標準訳語として `要求仕様` と呼ぶ。

本書でいう `望み` は、要求の手前にある「こうなってほしい状態」を説明する補助説明語である。要求や要求仕様は、その望みが設計・実装・検証のために明文化された形として扱う。

したがって、`願い`、`望み`、`要求`、`要求仕様` は次のように分ける。

- 望み: 到達したい状態、こうなってほしい状態。
- 願い / お願い: その状態へ向けて対象に渡す働きかけを生活語で説明する補助説明語。
- 要求: 満たされるべき条件や必要事項。
- 要求仕様: 要求を文書化し、設計・実装・検証の基準にしたもの。

### operation / 操作、control / 制御、cyber / 操る

`operation` は、標準訳語としては `操作`、文脈によっては `演算` や `処理` でよい。

ここでいう操作とは、対象に対して行う具体的な働きかけである。ボタンを押す、コマンドを入力する、値を変える、ファイルを開く、機械を起動する、といった個別の行為を指す。

`control` は、標準訳語としては `制御` でよい。対象の状態や出力を、望ましい範囲に保つ働きである。

本書でいう `cyber` / `操る` は、`operation` や `control` の標準訳ではない。状態を見て、望みを置き、操作や制御を選び、結果を見ながら整える一連の働きを、日本語の生活感覚で読むための補助説明語である。

したがって、`cyber = operation` ではない。`cyber = control` でもない。本書では、操作と制御を含みながら、対象を望む状態へ向けて扱う見方として `cyber` を読む。

## 4. 使い方の注意

読み換え語を使うときは、次を確認する。

1. その語は、本文の文脈で必要か。
2. 既存訳を消すのではなく、対応関係を示せているか。
3. 初出時に読みと意味を説明しているか。
4. 標準訳だと断定していないか。
5. 神秘化・宗教化の方向へ読者を引っ張っていないか。
6. カタカナ語を避けること自体が目的になっていないか。
7. 読者が、一般的な技術語へ戻って調べられる形になっているか。
8. `陰陽`、`陰陽師`、`陰陽術` を使う場合、数理、史料、伝承、現代文化、本文上の比較概念を混ぜていないか。

## 5. 本文へ反映する前の確認

このメモの語を本文へ入れるときは、次のように扱う。

- `terms_rereading_note.md` の内容をそのまま本文へ貼らない。
- 章ごとに必要な語だけを選ぶ。
- 読み換え語を先に立て、一般的な技術語を括弧や注で補う。
- ただし、一般的な技術語の方が読者に通じやすい箇所では無理に置き換えない。
- 著者の新しい指示があれば、このメモより優先する。
