# 第7部　スマートデバイス、魔法、魔人

## 第7章　スマートデバイス設計の見え方を変える

スマートデバイスを作るには、具体的な仕様を決めなければならない。

カメラを載せるのか。マイクを載せるのか。どのセンサーを使うのか。処理は端末側で行うのか、クラウドで行うのか。画面を持たせるのか、音声で返すのか、プロジェクターで空間へ表示するのか。どの家電やサービスと接続するのか。どこまで自動化し、どこで人間に確認を求めるのか。

こうした問いは、スマートデバイス設計の本体である。

本章は、それらの問いを否定しない。

むしろ本章で扱うのは、そうした問いが何を意味しているのかを、別の言葉で見えやすくすることである。

英語由来の技術語やカタカナ語のままでは、設計意図が見えにくいことがある。センサー、AI、クラウド、UX、IoT、アクチュエータ、API、エッジ処理、コンテキスト認識。どれも必要な語であり、間違った語ではない。しかし、それらを聞いた人が、生活の中で何が起きるのか、何を叶える装置なのかを直感しにくい場合がある。

ここで、前章までの議論が効いてくる。

デジタル技術を日本語の身体感覚で捉え直すと、それは、状態を読み、記号や作法を通じて働きを呼び、代理的なものに仕事をさせ、現実の状態を変える技術として見えてくる。

この見え方は、陰陽師的、魔法的、式神的に聞こえるかもしれない。

しかし、それは神秘化ではない。

スマートデバイス設計の内容そのものを変えるためではなく、すでに行われている設計議論の意図を、生活感覚の中で見えやすくするための補助線である。

## 7.1 ここで陰陽師の話をしていた理由

なぜ、ここまで陰陽師や魔法のように聞こえる話をしてきたのか。

それは、スマートデバイスを設計するときに、何を作ろうとしているのかを感覚的に掴むためである。

「陰陽師的に見る」とは、歴史上の陰陽師そのものを持ち出すことではない。宗教的な陰陽術をデジタル技術へ重ねることでもない。

ここでいう陰陽師的な見方とは、次のような操作イメージである。

- 状態を読む
- 兆しを見る
- 符号や作法を扱う
- 条件が整ったときに働きを呼ぶ
- 代理的なものに仕事をさせる
- 場を整える
- 願いを現実の状態変化へつなげる

この見方を持つと、スマートデバイスの設計で行われている普通の議論が、別の姿で見えてくる。

カメラを載せるという議論は、何を見る目が必要かという議論に見える。

マイクを載せるという議論は、どの願いを聞き取る耳が必要かという議論に見える。

センサーを選ぶという議論は、どの状態や兆しを読む必要があるかという議論に見える。

AIを接続するという議論は、願いを解釈し、手順へ分け、外部の道具へ働きを渡す代理演算体を置く議論に見える。

プロジェクターやディスプレイを使うという議論は、その代理演算体の姿や状態や結果を、どこにどう現すかという議論に見える。

安全範囲や権限を決めるという議論は、どこまで働いてよいかという結界を張る議論に見える。

つまり、陰陽師の話は、スマートデバイス設計に別の正解を押しつけるためではない。

同じ設計内容を、身体感覚に即した言葉で見えやすくするためにある。

## 7.2 既存の設計議論と本章の議論は対立しない

スマートデバイスの設計では、部品、性能、価格、量産性、安全性、通信、電池、アプリ、サービス連携を考えなければならない。

これは当然である。

カメラの解像度が足りなければ、必要な状態は読めない。マイクの性能が足りなければ、声は拾えない。通信が不安定なら、外部サービスとつながらない。電池が持たなければ、生活の中では使いにくい。筐体が大きすぎれば、身につけられない。安全機構が弱ければ、現実へ作用させることはできない。

だから、本章は「部品や機能から考えるのは間違いだ」と言う章ではない。

むしろ、部品や機能の議論は必要である。

ただ、その議論を利用者や設計の入口にいる人へ説明するとき、部品名や技術名だけでは、その部品が何のために必要なのかが見えにくい。

そのとき、見方を変える。

これは何を見るための目なのか。

これは何を聞くための耳なのか。

これは誰の願いを、どの術へ渡すための入口なのか。

これはどの代理演算体を、どこに現れさせるための器なのか。

これはどの現実の状態を変えるための手足なのか。

この問いに言い換えると、既存の設計議論は、生活感覚の中で理解しやすくなる。

## 7.3 魔法とは、設計意図が体験として見えることである

本章では、魔法という比喩を使う。

ただし、ここでいう魔法は、神秘的な力のことではない。

魔法とは、人の「こうなってほしい」という願いが、記号、演算、AI、デバイス、表示、空間配置を通じて、現実の状態変化として現れる体験のことである。

部屋が明るくなる。必要な情報が壁に出る。話しかけると、AIが文脈を読んで次の手順を示す。手をかざすと入力が開く。危ない状態になる前に止まる。遠くの人と同じ状態を見る。複雑な手順を意識しなくても、場が整う。

これらは、技術的にはセンサー、認証、通信、AIの推論、API、表示、ログ、安全制御の組み合わせである。

その説明は正しい。

しかし利用者には、その内部機構が一つずつ見えるわけではない。利用者には、「頼んだら整った」「近づいたら反応した」「合図したら現れた」「必要なものがその場に出た」という体験として現れる。

この体験を、比喩的に魔法と呼ぶ。

魔法という言葉を使うのは、技術説明を曖昧にするためではない。むしろ、部品や機能の奥にある設計意図を、生活感覚へ戻すためである。

## 7.4 魔人とは、AIエージェントの働きが見えた姿である

同じように、魔人という比喩も使える。

ここでいう魔人は、本当に人格を持つ存在ではない。願いを叶える万能の存在でもない。

魔人という比喩が指しているのは、呼び出され、願いを聞き、文脈を読み、手順を組み立て、外部の道具を使い、結果を返す代理演算体である。

これは、第6章で述べたAIエージェントの働きに近い。

AIエージェントは、人の願いをそのまま現実へ変えるわけではない。人の言葉は曖昧であり、装置がそのまま実行できる形式ではない。

「見やすくしてほしい」

「会議しやすくしてほしい」

「この場に必要な情報だけ出してほしい」

「危ないときは止めてほしい」

こうした願いを受け取ったAIエージェントは、状況を読み、条件を確認し、使える道具を選び、実行可能な手順へ分ける。

技術的には、これはAIエージェント、ツール実行、API連携、状態管理、権限管理の話である。

感覚的に言えば、人の願いを聞いて働く魔人や式神のように見える。

本章で重要なのは、「AIは本当に魔人である」と言うことではない。

AIエージェントの設計意図を、日本語の生活感覚で見ると、そのように見えることがある、ということである。

## 7.5 願い、術、器、仕様

ここで、本章の見取り図を置く。

```text
願い -> 術 -> 器 -> 仕様
```

この順序は、既存の仕様策定を否定するものではない。

最終的には、仕様書を書く。部品を選ぶ。筐体を設計する。コストを見積もる。電池容量を決める。通信方式を選ぶ。安全要件を定める。

本章でしているのは、その仕様の背後にある意図を、感覚に即した言葉で読み直すことである。

まず、願いがある。

こうなってほしい。これを見たい。これを見せたい。これを安全に動かしたい。この場を整えたい。AIに現実の中で案内してほしい。

次に、その願いを叶えるための術がある。

入力する。状態を見る。見せる。きっかけで動かす。外部とつなぐ。量や向きを与える。相互作用させる。繰り返し呼び出す。複数のものを同時に扱う。動きの勢いを整える。

その術を現実に通すために、器がいる。

器とは、スマートデバイスである。マイク、カメラ、センサー、スピーカー、ディスプレイ、プロジェクター、アクチュエータ、通信、API、ログ、安全機構を備えた、現実へ作用するための場である。

そして最後に、仕様が決まる。

このカメラは、どの状態を見るために必要なのか。このマイクは、どの願いを聞くために必要なのか。このプロジェクターは、どの状態や代理演算体の姿を場に出すために必要なのか。この通信は、どの術を外部へ通すために必要なのか。この安全機構は、どこまで働いてよいかを示すために必要なのか。

こう読み直すと、仕様は単なる項目の集合ではなく、願いを現実の状態変化へつなぐための構造として見える。

## 7.6 器として見たときの対応表

スマートデバイスを器として見ると、すでにある設計項目が別の言葉で見えてくる。

| 器としての見え方 | 技術的には |
|---|---|
| 目 | カメラ、センサー、状態取得、ログ |
| 耳 | マイク、音声認識、イベント入力 |
| 声 | スピーカー、音声応答、通知 |
| 姿 | ディスプレイ、プロジェクション、アバター、状態表示 |
| 手足 | アクチュエータ、家電制御、ロボット、API |
| 通路 | 通信、プロトコル、デバイス連携、外部サービス接続 |
| 記憶 | ログ、履歴、設定、ユーザー文脈、RAG |
| 結界 | 権限、安全範囲、停止条件、プライバシー、失敗時の動作 |
| 換装性 | 更新、拡張、ライブラリ差し替え、外部エージェント接続 |

この表は、技術的な用語を捨てるためのものではない。

むしろ逆である。

技術的な用語が指している働きを、生活感覚で読みやすくするための表である。

「カメラを載せる」と言っても、それだけではなぜカメラが必要なのか分かりにくいことがある。「何を見る目が必要なのか」と言い換えると、必要な画角、解像度、設置位置、プライバシー条件が見えやすくなる。

「プロジェクターを使う」と言っても、それだけでは映像装置の話に聞こえる。「どこに姿や状態を現すのか」と言い換えると、投影距離、明るさ、位置合わせ、複数人で見えること、物体のそばに表示することの意味が見えやすくなる。

「権限管理をする」と言っても、それだけではセキュリティ項目に見える。「どこまで働いてよいかを示す結界」と言い換えると、停止条件、確認要求、プライバシー、安全範囲が、利用者の安心と結びついて見える。

本章で行っているのは、この種の読み直しである。

## 7.7 杖とランプの比喩

現行稿にある「魔法のない杖」「魔人のいないランプ」という比喩は、この章でも使える。

ただし、これは既存のデバイス開発を批判するための言葉ではない。

言いたいのは、部品や筐体の価値は、それが通す術や呼び出す代理演算体と結びついたときに、利用者へ伝わりやすくなる、ということである。

杖が軽いこと、美しいこと、持ちやすいことは大事である。

しかし、その杖で何が起こせるのかが見えると、軽さや形や材質の意味も分かりやすくなる。

ランプが美しいこと、丈夫なこと、持ちやすいことも大事である。

しかし、そこから何が呼び出され、何をしてくれるのかが見えると、ランプの形や置き場所や呼び出し方の意味も分かりやすくなる。

スマートデバイスも同じである。

センサーの精度、筐体の軽さ、表示の美しさ、電池持ち、通信安定性は、それだけでも重要である。だが、それがどの願いを、どの術を通して、どの現実の変化へつなげるのかが見えると、その重要性はさらに理解しやすくなる。

## 7.8 `sword-voice-agent` をどう見るか

`sword-voice-agent` は、この見方を小さく示す例として扱える。

刀印で入力ゲートを開く。音声で願いを伝える。AIエージェントが文脈を読み、手順を組み立てる。アバター、音声、投影表示、家電操作、外部サービス接続へつなぐ。

技術的に言えば、これはジェスチャー入力、音声認識、AIエージェント、状態表示、プロジェクション、デバイス連携の組み合わせである。

その説明は正しい。

同じものを本章の言葉で見ると、次のようになる。

刀印は、入力を開く契である。

音声は、願いを渡す経路である。

AIエージェントは、願いを手順へ変える代理演算体である。

プロジェクションは、代理演算体の姿や状態を場に現す器官である。

家電操作や外部サービス接続は、現実へ触れる手足である。

権限や停止条件は、結界である。

この例で重要なのは、刀印が和風だから面白いということではない。

同じ設計を、技術項目の一覧としても、願い、契、代理演算体、器、結界の流れとしても読める、ということである。

## 7.9 第8章への接続

ここまで、スマートデバイスを、AIエージェントやサイバーの術が現実に触れるための器として読み直した。

この読み直しは、AI側だけで終わらない。

AIエージェントがスマートデバイスを器として使うなら、人間もまた、AI、記録、プロンプト、表示装置、スマートデバイスを外部器官として使っている。

記憶を外に置く。判断を補助する。状態を表示する。行為を支える。必要な情報を場に出す。身体や脳だけに閉じていた働きを、機械や記録やAIへ逃がす。

これは、第8章のサイボーグ、外部器官、生き残る身体の話につながる。

スマートデバイスは、AIにとって現実へ触れる器である。同時に、人間にとっても、記憶、判断、表示、行為を外へ広げる器官になりうる。

## 7.10 仮結論

第7章で言いたいのは、既存のスマートデバイス設計論が間違っているということではない。

カメラ、マイク、センサー、AI、通信、表示、電池、筐体、安全機構を考えることは必要である。

ただし、それらを技術語のまま並べるだけでは、何を実現しようとしているのかが見えにくくなることがある。

デジタル技術を日本語の身体感覚で捉え直すと、同じ議論は別の姿で見えてくる。

カメラは目に、マイクは耳に、プロジェクターは姿に、APIやアクチュエータは手足に、権限や停止条件は結界に見える。

AIエージェントは、願いを受け取り、手順へ変え、外部の道具を使う代理演算体として見える。

スマートデバイスは、その代理演算体やサイバーの術を、現実の場に通す器として見える。

この見方は、設計の内容を別物にするためではない。

同じ設計意図を、感覚に即した言葉で理解しやすくするためである。

その意味で、前章までの陰陽師的な話は、ここで回収される。

状態を読み、符号や作法を扱い、代理的なものに働かせ、場を整え、現実の状態変化へつなげる。その見方を持つと、スマートデバイス設計は、部品や仕様の羅列ではなく、願いを現実へ通す器の設計として見えてくる。

- 既存のスマートデバイス設計、UX論、IoT機能設計、部品選定を否定しない構成にした。

マージ時に注意すること。

- この章は「こう設計しろ」と命じる章ではない。
